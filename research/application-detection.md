# Automatic application detection from traffic and process evidence

Research note, 2026-11-06. Status: research only, nothing built.
Scope: can a Claude skill that reads an Illumio PCE through the illumio-mcp
server group workloads into applications when hostnames and labels do not
say what they are, and is it worth an experiment.

## Summary for the owner

Yes, this is worth building as a small, clearly flagged experiment, but not
as a feature of the label advisor. Every product that does this (Cisco Secure
Workload, Akamai Guardicore, ServiceNow, Illumio's own Core Services Detector
and cloud AI Labeling) ships it as a suggestion with a confidence and a
human accept or reject step, and none of them documents an algorithm beyond
"flows plus processes plus hostnames, then clustering"; Cisco's patent is the
only concrete one and it is an MDL-scored partition of a flow graph. The
single most promising approach for Illumio is a hybrid: strip infrastructure
hubs first (computed at workload level, because the server's
`identify-infrastructure-services` only works on app-labelled flows), then
run label propagation or Louvain over the pruned workload graph seeded with
the labels that already exist, and name each cluster from hostname tokens
and existing labels or hand the user a placeholder. All of that fits in a few
hundred lines of stdlib Python and runs in seconds on a few thousand
workloads; the hard part is not the algorithm but assembling a full graph
through 500-flow queries and keeping shared databases, load balancers and
monitoring pollers from smearing clusters together. Evaluation is possible on
any partially labelled estate by treating existing app labels as held-out
ground truth and scoring pairwise precision (do not merge apps) ahead of
recall (fragmentation is cheap to fix by hand). Build it as a separate
experimental skill that writes a cluster report plus candidate Illumio
labeling rules, which the advisor can then consume; do not put a clustering
mode inside the advisor until the experiment has numbers.

## 1. What the MCP server gives us (verified in source)

Facts checked in `/Volumes/MacMini-4TB/alex-extern/git/illumio-mcp-server`
on 2026-11-06, because the feasibility argument rests on them.

- `get-workloads` with `detail_level=full` returns the PCE workload record
  including `services.open_service_ports`, and the SDK model for each port
  carries `port`, `protocol`, `address`, `user`, `package`, `process_name`
  and `win_service_name` (illumio-py `workloads/workload.py`). So listening
  port plus process name per workload is available without traffic.
  `compact` is the default and omits services; `full` output is truncated
  at `MCP_MAX_RESPONSE_BYTES` (800 KB, `tools/constants.py`) with no offset
  parameter, so full detail has to be pulled in batches (by label, hostname
  or `ip_address` prefix) rather than in one call.
- `get-traffic-flows` pins `max_results` to 500 per call. It accepts
  `include_sources`, `include_destinations`, `exclude_*` (label shorthand,
  label, IP list or workload HREFs, IPs), `include_services` and
  `exclude_services` (port and proto), `policy_decisions`, and a `group_by`
  over process, service_name, user, source, source_app, destination,
  dest_app, fqdn, ip_list, port, proto, policy, rule, direction. Rows carry
  `process_name`, `src_hostname`, `dst_hostname`, `dst_fqdn`,
  `policy_decision`, `num_connections`. Cap hit means
  `total_pce_flows == 500`.
- `identify-infrastructure-services` builds its graph from `src_app`,
  `dst_app`, `src_env`, `dst_env` and drops rows where either side lacks
  them (`tools/ringfence.py`, `handle_identify_infrastructure_services`).
  It scores nodes by normalised in-degree, out-degree, Brandes betweenness
  and connection volume, with a "provider" pattern (high fan-in: AD, DNS,
  shared DB) and a "consumer" pattern (high fan-out: monitoring, backup),
  dampens mixed-traffic nodes and halves non-production scores. On an
  unlabelled estate it returns "no labeled app flows". The idea is right,
  the unit is wrong for our case: we need the same scoring per workload.
- User rule from memory: a script may post-process saved JSON but never
  calls the PCE; gaps become server issues.

## 2. Prior art in products

Legend: "documented" means stated in vendor documentation or a patent;
"inferred" is my reading. Marketing claims are marked as such.

### Cisco Secure Workload (formerly Tetration)

- Signals (documented): "Advanced users can choose the main source of data
  for clustering algorithms, that is, live network flows, or running
  processes, or both." Agent-based sensors give the best signal; NetFlow
  loses client-server direction. Side information can be uploaded (F5,
  NetScaler, HAProxy load balancer configs, route labels) and "the clustering
  results generated by automatic policy discovery never span the subnet
  boundaries as defined by the uploaded data." Clusters never span
  partitions. (https://securitydocs.cisco.com/docs/csw/3-10/user/92268.dita,
  https://securitydocs.cisco.com/docs/csw/3-10/user/92226.dita)
- Algorithm (documented in patent US20160359697A1, "MDL-based clustering for
  application dependency mapping"): nodes are source endpoints, destination
  endpoints and destination ports; edges are observed flows; candidate
  clusterings are scored by minimum description length over the combination
  of source cluster, destination cluster and port cluster, and the minimum
  score picks the number of clusters; a randomised local search improves the
  clustering within each partition; partitions come from routing
  information, subnet masks or regions and zones.
  (https://patents.google.com/patent/US20160359697A1/en)
- Naming and confirmation (documented): discovery "examines the hostnames
  and labels that are associated with workloads. For each cluster, automatic
  policy discovery generates a short list of candidate queries" the user
  picks and edits; clusters "have a confidence rating that helps you
  evaluate whether the workloads in the group belong together"; approving a
  cluster freezes its query, later runs only touch unapproved workloads, and
  "approving known good clusters ... can improve the clustering of other
  workloads upon rerun". A granularity knob (very coarse to very fine)
  controls cluster size.
  (https://securitydocs.cisco.com/docs/csw/3-10/user/92226.dita,
  https://securitydocs.cisco.com/docs/csw/3-10/user/92273.dita,
  https://securitydocs.cisco.com/docs/csw/3-10/user/92245.dita)
- Takeaway: the closest analogue to what we want. Note the design choices:
  partition before clustering, express a cluster as a membership query the
  user can read, confidence per cluster, approval as seed for the next run.

### Akamai Guardicore Segmentation

- Signals (documented in vendor blog): AI Labeling "leverages generative AI
  capabilities to suggest appropriate labels based on process
  communications"; the model infers "the most likely identity for a machine
  that has specific processes communicating"; each suggestion carries a
  confidence score and an explanation, and the advice is to act only on the
  most confident ones.
  (https://www.akamai.com/blog/security/2024/may/accelerating-zero-trust-outcomes-with-generative-ai-part-1)
- Earlier auto-labeling (vendor blog, 2020): "relies on flow analysis down
  to the process level" and recommends labels for discovered applications.
  (https://www.akamai.com/blog/security/ai-powered-segmentation-cloud-native-security)
- Confirmation (documented, third-party copy of a 2023 TechDocs page, so
  treat with care): suggestions are for Application and Role label keys,
  applied only after approval, merged into an existing label if one matches,
  with an Origin column showing user versus AI.
  (https://www.cliffsnotes.com/study-notes/15705542)
- Takeaway: process names are the primary signal for naming, traffic for
  grouping; confidence plus explanation per suggestion. No algorithm
  disclosed.

### ServiceNow Discovery and Service Mapping

- Three mapping modes (documented): top-down from an entry point, tag-based
  (groups components by tag but "does not identify relationships"), and
  traffic-based ("following traffic connections between them"). Traffic-based
  discovery is off by default; with Predictive Intelligence it adds
  connections by connection rules, and the docs warn it can create duplicate
  connections and should be turned off after tuning.
  (https://www.servicenow.com/docs/r/it-operations-management/service-mapping/service-mapping-get-started.html,
  https://www.servicenow.com/docs/r/AGMjjjnYvvG0sY5d7GEnIw/RougygcWO18_79i4YMMFSg)
- ML candidates (vendor community post): "traffic fingerprinting" creates
  "process clusters"; the user opens Application Service Candidates, previews
  the map and creates the service with one click; entry points are
  calculated automatically. No algorithm or naming detail.
  (https://www.servicenow.com/community/itom-blog/automated-service-suggestions-machine-learning-is-supercharging/ba-p/2372224)
- Noise (patent US11132613B2): a decision tree labels each traffic-based
  connection keep or remove using port category and source and target
  process categories; the examples of noise are database backup traffic and
  a common monitoring tool, "if all applications use a common monitoring
  tool to report their status"; a reason-code interface explains each
  decision. (https://patents.google.com/patent/US11132613B2/en)
- Takeaway: the vendor with the longest history here treats raw traffic as
  unreliable by default and spends its ML budget on removing edges, not on
  finding clusters. That ordering matters for us.

### Dynatrace Smartscape

- Topology (documented): five tiers (applications, services, processes,
  hosts, data centres); process-to-process edges come from captured TCP/IP
  requests; unmonitored peers appear as "monitoring candidates"; edges are
  dropped after 72 hours of inactivity.
  (https://docs.dynatrace.com/docs/platform/smartscape)
- Grouping (documented): processes are grouped into process groups by
  built-in detection rules on executable, command line, Java system
  properties, environment variables and container metadata; custom rules
  split or merge groups; naming is a separate rule set from detection.
  (https://docs.dynatrace.com/docs/shortlink/process-groups)
- Takeaway: Dynatrace does not cluster traffic at all. Application identity
  comes from process attributes and explicit rules, and edges are only
  drawn. This is the "role from process, app from rules" school, and it is
  a reminder that process evidence is more precise than traffic evidence.

### What the prior art agrees on

1. Inputs are always the same three: flows, process names, hostnames or
   tags; existing labels are used as seeds where available.
2. Nobody publishes a clustering algorithm beyond Cisco's MDL patent; the
   observable product behaviour is a partition plus a per-cluster
   confidence.
3. Noise removal before grouping is treated as the core problem (ServiceNow
   patent, Illumio core services, Cisco partitions and side information).
4. Output is a suggestion with explanation and an accept or reject step,
   and approved results become durable rules or queries, never a direct
   write.

## 3. Algorithms

Working graph for this section: nodes are managed workloads (a few
thousand), edges are aggregated flows between two managed workloads,
weighted by number of connections or distinct (port, proto) pairs. Unmanaged
IPs stay out of the clustering and are attached to clusters afterwards.

### 3.1 Community detection on the traffic graph

Louvain (Blondel et al. 2008): greedy modularity optimisation, local node
moves then aggregation, repeated. The authors report it ran on a 118
million node web graph and it is the default in most tools.
(https://arxiv.org/abs/0803.0476)

- Stdlib feasibility: yes, about 120 to 180 lines (adjacency dict, node
  degree, community totals, modularity gain per move, aggregation pass).
- Complexity: each level is roughly O(E) per sweep with a handful of
  sweeps; on 3,000 nodes and 100,000 aggregated edges pure Python finishes
  in seconds.
- Known failures: results depend on node order; communities can be badly
  connected or even disconnected (Traag et al. 2019 measured "up to 25% of
  the communities are badly connected and up to 16% are disconnected" for
  Louvain, https://arxiv.org/abs/1810.08473); the resolution limit means
  modularity "may fail to identify modules smaller than a scale which
  depends on the total number L of links" (Fortunato and Barthelemy 2007,
  https://arxiv.org/abs/physics/0607100). For us the resolution limit means
  small applications (three to five workloads) get swallowed by big ones
  unless a resolution parameter is added, which is a one-line change to the
  gain formula.

Leiden (Traag, Waltman, van Eck 2019): Louvain plus a refinement phase;
"yields communities that are guaranteed to be connected" and "runs faster
than the Louvain algorithm". (https://arxiv.org/abs/1810.08473)

- Stdlib feasibility: yes but roughly double the code (refinement with
  randomised merges inside each community, then aggregation on the refined
  partition); 250 to 350 lines and easy to get subtly wrong. For a few
  thousand nodes the connectivity guarantee can be had more cheaply by
  running Louvain and then splitting any community into its connected
  components, which is what I would do first.

Label propagation (Raghavan, Albert, Kumara 2007): every node starts with
its own label and repeatedly adopts the label most of its neighbours hold;
near-linear time; no objective function and no community count needed.
(https://arxiv.org/abs/0709.2938)

- Stdlib feasibility: trivially, 30 to 50 lines.
- Complexity: O(E) per iteration, usually under 20 iterations.
- Known failures: non-deterministic; label epidemics produce one "monster"
  community. Leung et al. 2009 add hop attenuation and node preference to
  stop "label epidemic" and report that attenuation "deters the occurrence
  of the monster clusters". (https://arxiv.org/abs/0808.2633)
- Why it still matters for us: label propagation is the natural
  semi-supervised variant. Seed nodes with existing app labels and keep
  those fixed (the Zhu and Ghahramani 2002 formulation, where given labels
  stay clamped and the propagated labels converge; summarised in
  https://arxiv.org/abs/1307.0252). On a partially labelled estate this
  turns "cluster then name" into "spread the names we already have", which
  is exactly what the label advisor wants.

Connected components after pruning shared infrastructure: remove hub nodes
and low-weight edges, then take components.

- Stdlib feasibility: 20 lines (BFS).
- Complexity: O(V + E).
- Known failures: one surviving shared edge merges two applications; one
  chatty ETL job merges a whole data platform. It is useless alone and
  excellent as the first cut after hub removal, and as the splitter after
  Louvain.

### 3.2 Similarity clustering on feature vectors

Build a feature set per workload and cluster workloads with similar sets.
Candidate features:

- peer set: the set of (peer, port) it talks to and is talked to by, after
  hub removal;
- port signature: listening ports from `open_service_ports`;
- process signature: process basenames from `open_service_ports` and from
  traffic `process_name` (the server's `process_basename` already strips
  paths);
- hostname tokens (section 4);
- subnet (/24 or the site's actual prefix lengths);
- existing labels of the workload, if any.

Similarity: Jaccard over sets, or weighted Jaccard with TF-IDF style
down-weighting of tokens shared by most of the estate (a port 445 listener
says little, a port 1521 listener says a lot). Clustering: single-link or
average-link agglomerative with a threshold, or simply "connect pairs above
threshold and take components".

- Stdlib feasibility: yes. Set intersections are built in; an inverted
  index from feature to workloads avoids the naive all-pairs loop; 100 to
  150 lines.
- Complexity: naive all-pairs on 3,000 nodes is 4.5 million set
  intersections, which is acceptable in Python (tens of seconds); with the
  inverted index it is proportional to the number of shared features.
- Known failures: workloads that look alike are not the same application
  (every IIS web tier looks like every other IIS web tier). This method
  finds roles and templates, not applications. The literature is explicit
  that structural roles and communities are different and complementary
  (RolX, Henderson et al. 2012,
  https://research.google/pubs/rolx-structural-role-extraction-mining-in-large-graphs/),
  and BLINC showed that transport-level host behaviour alone classifies
  server roles with over 95% accuracy on real traces, without payload or
  port knowledge (Karagiannis et al. 2005,
  https://www.microsoft.com/en-us/research/?p=153407). So this is the tool
  for the role dimension, not the app dimension.

### 3.3 Hybrid pipelines

What the products do, and what the research says works: the dependency
discovery papers all learned that pure traffic co-occurrence is noisy.
Orion (Chen et al. 2008) found that proxies and co-running clients create
false dependencies ("the Exchange client has false dependency on the proxy
service"), aggregated clients into clusters using "server naming
conventions", and still needed about a day of manual confirmation for 158
candidates. (https://static.usenix.org/events/osdi08/tech/full_papers/chen_xu/chen_xu_html/index.html)
Macroscope (Popa et al. 2009) improved on packet-trace-only methods by
"combining application process information with network level packet
traces" and reported less human involvement.
(https://researchr.org/publication/PopaCSCT09/bibtex)

The hybrid that fits Illumio: traffic graph for grouping (app), feature
similarity for role, hostname tokens and subnet for env and loc and for
naming, existing labels as seeds and as evaluation. Details in section 6.

### 3.4 Failure modes and the fix for each

| Failure | What it does to clusters | Mitigation |
|---|---|---|
| Provider hubs (AD, DNS, NTP, LDAP, SMB to DCs, shared DB, proxy, mail relay) | Every cluster touches them, so modularity merges around them | Remove edges to any (dst, port) with distinct-source fan-in above a threshold before clustering; Illumio's 51 core services list and the port-matching method are the model |
| Consumer hubs (monitoring pollers, vulnerability scanners, backup, config management, jump hosts) | One source reaches everything, acts as glue | Remove edges from any source with distinct-destination fan-out above a threshold on the same port; ServiceNow's patent names "a common monitoring tool" as the canonical noise |
| Load balancers and VIPs | Clients talk to a VIP (often unmanaged), servers see the LB as the only client; the tier splits from its consumers | Cisco accepts LB configs as side information; we can only note VIP-fronted clusters and ask; the Illumio virtual service objects could be read if the server exposes them (it does not today) |
| Shared databases serving several apps | Merges the apps that share it | Treat a DB listener with many distinct client clusters as a provider hub after a first pass (two-pass hub removal) |
| ETL, batch, message buses | Legitimately cross-app edges | Down-weight edges that carry few distinct ports or only one process; let the user cut |
| Resolution limit | Small apps absorbed | Resolution parameter above 1; split communities by components and by hostname token disagreement |
| Query cap | Hub destinations truncate at 500 rows, so hub edges are under-counted exactly where it matters | Query from the source side per workload, and treat `total_pce_flows == 500` as "hub, requery by port" |
| Partial visibility | Idle VENs and short windows under-report; Windows process names vary by path | Use 30 to 90 days, basename processes, and require edge support in both directions where possible |

## 4. Hostname token mining

There is no published method aimed at enterprise server names for app, env
and loc; the closest published work is CAIDA's router hostname geolocation,
which is the same problem (operators embed codes in names, each domain has
its own convention) and documents heuristics that transfer directly.

DRoP (Huffaker, Fomenkov, claffy 2014): "We strip the common public suffix
part of the name, split the remainder into substrings (truncating
non-alphabetic characters), and count the distance from each substring to
the stripped suffix"; a candidate is [suffix, substring, position]; the
assumption is that "each autonomous naming domain uses geographic hints
consistently within that domain"; a rule is created for a suffix "if more
than 60% of such geohints are likely valid"; conflicting rules are resolved
by keeping the one matching more hostnames; 1,711 rules over 1,398 domains,
validated against six operators' naming schemes with up to 99% accuracy
where measurements were sufficient.
(https://www-old.caida.org/publications/papers/2014/drop/drop.pdf)

Hoiho (Luckie et al. 2021) replaced DRoP's fixed-position assumption with
learned regular expressions: it builds candidate regexes per suffix,
evaluates them against training data, penalises inconsistency, and rates a
naming convention "good if it extracted at least three unique location hints
consistent with training data with a PPV >= 90%, promising ... with a PPV
>= 80%, and poor otherwise". It also learns operator-specific mnemonic codes
not in any dictionary, and correctly geolocated 94.0% of hostnames with a
hint versus 56.6% for DRoP. (https://par.nsf.gov/servlets/purl/10322969)

Practitioner conventions (not research, but they tell us what to expect):
schemes such as Location-Function-Environment-Sequence (NYC-WEB-PROD-01),
Function-Environment-Location-Sequence (DBTSTLON02), [svc]-[env]-[role][nn]
with a 15-character Windows limit, and compact forms like ukinmailp1 where a
single character carries the environment.
(https://arb.oit.uci.edu/oit/hostnames.html,
https://devcentral.f5.com/s/articles/thoughts-on-hostname-nomenclature)

Heuristics to implement (all stdlib):

1. Strip the DNS suffix; split on `-`, `_`, `.` and on letter-digit
   boundaries; keep the digit run as a sequence token; keep a copy of the
   raw string for fixed-width conventions (positional slicing when there
   are no separators, as in ukinmailp1).
2. For each (token, position-from-left, position-from-right) count
   workloads; a token that appears in 2 to 30% of hosts at a stable
   position is a candidate app or site code; a token in more than half of
   hosts is a convention prefix (company code) and is dropped; a token that
   only ever appears once is a sequence or a one-off.
3. Dictionary pass against existing label values (app, env, loc and custom
   keys), common env markers (prd, prod, p, dev, d, tst, test, t, uat, qa,
   stg, stage, s), common role markers (web, app, db, sql, ora, dc, fs, mq,
   api, lb, prx) and a small site list the user supplies or the labels
   already contain. This is DRoP's dictionary step with Illumio labels as
   the dictionary.
4. Position consistency: a dictionary hit is a rule candidate only if the
   same category sits at the same position for most hosts with that prefix
   (DRoP's 60%, Hoiho's 80 to 90% PPV against already-labelled hosts).
5. Emit each accepted rule as an Illumio labeling-rule candidate (hostname
   regex, label), which is a durable artefact the user can read and Core
   25.4 can run.
6. Cross-check tokens against traffic clusters: a cluster whose members
   share a token not shared by the neighbours is probably well named; a
   token spread across several clusters is a site or env token, not an app.

## 5. Evaluation on a partially labelled estate

Ground truth: workloads that already carry an app label (and env, loc for
those dimensions). Compare the clustering restricted to labelled workloads
against the label partition. If labels were used as seeds, hold out a random
third of labelled workloads, cluster with the rest as seeds, score on the
held-out third, repeat with three splits.

Metrics, with the caveats that matter here:

- Pairwise precision and recall (Fowlkes-Mallows is their geometric mean):
  TP are pairs together in both, FP pairs together in the clustering but
  not in the labels, FN the reverse.
  (https://scikit-learn.org/stable/modules/clustering.html) These are the
  right primary metrics because the costly error in segmentation is a
  merge (two apps under one label widens a ring fence) and the cheap error
  is a split (user merges two clusters in review). Report precision ahead of
  recall.
- Adjusted Rand index: "corrects for chance", range -0.5 to 1, random
  labelling scores near 0; the unadjusted index "is often close to 1.0 even
  if the clusterings themselves differ significantly", so never report plain
  RI. (https://scikit-learn.org/stable/modules/clustering.html)
- Purity per cluster: fraction of a cluster's labelled members carrying the
  majority label. It "doesn't penalize having many clusters" and "doesn't
  work well for imbalanced data" (https://en.wikipedia.org/wiki/Cluster_analysis),
  so use it only as the per-cluster confidence shown to the user, never as a
  global score.
- Homogeneity and completeness (V-measure) read as "clusters are pure" and
  "apps are not fragmented"; scikit-learn warns they are "not normalized
  with regards to random labeling" and that for small samples or many
  clusters "it is safer to use an adjusted index such as the Adjusted Rand
  Index". Our case is exactly that (hundreds of apps), so ARI and pairwise
  scores lead.
- BCubed precision and recall are the per-item form of the pairwise
  metrics and the only family satisfying all of Amigo et al.'s formal
  constraints; worth computing because it does not over-weight big apps.
  (https://portalcientifico.uned.es/documentos/5fa07b08299952440aae188b?lang=en)

All of these are 20 to 40 lines each in stdlib.

What "good enough to suggest" looks like (my proposal, no published standard
exists):

- Pairwise precision at or above 0.8 on held-out labelled pairs, and
  per-cluster purity at or above 0.8 for any cluster that gets a proposed
  name. Below that, show the cluster with a placeholder and no name.
- Pairwise recall at or above 0.5. Fragmentation into two or three pieces
  per app is acceptable for a first pass; worse than that means hub removal
  was too aggressive or the resolution too fine.
- ARI at or above 0.5 on the labelled subset as a sanity floor; near 0
  means the traffic graph does not carry application structure on this
  estate and the experiment should stop there.
- Baselines to beat: hostname-token clustering alone, traffic alone, and
  "one cluster per /24". If the hybrid does not beat the best single
  signal, it is not earning its complexity.
- Report truncation: how many source workloads hit the 500 cap, and how
  many edges were dropped as hubs. A high cap rate invalidates the recall
  number.

## 6. Recommended experimental pipeline for Illumio

Order of steps, each producing a saved JSON file so the script never
touches the PCE:

1. Inventory. `get-workloads` at `labels_only` for breadth, then `full` in
   batches (by label, hostname prefix or enforcement mode) for
   `open_service_ports`. Save hostname, href, interfaces, labels, listening
   (port, proto, process basename, user).
2. Hostname mining (section 4) on the inventory alone. Emit token tables,
   candidate labeling rules, and a provisional env and loc per workload.
   This step costs no traffic queries and on many estates already answers
   env and loc.
3. Traffic collection. Per source workload (or per source label or
   hostname-prefix group where the estate is partly labelled),
   `get-traffic-flows` with `include_sources`, `group_by` of source,
   destination, port, proto, process, `policy_decisions` all three, 30 to
   90 days. Record any call where `total_pce_flows == 500` and requery it
   split by `include_services` port ranges. Keep only rows whose
   destination is a managed workload for the graph; keep unmanaged
   destinations in a side table for later attachment.
4. Hub removal at workload level. Compute per (dst, port) the number of
   distinct source workloads and per source the number of distinct
   destination workloads; flag providers above a fan-in threshold (start at
   20% of managed workloads or 50 sources, whichever is smaller) and
   consumers above a fan-out threshold; add a port-matching list seeded
   from Illumio's core services (DNS 53, Kerberos 88, LDAP 389 and 636,
   SMB 445 to DCs, NTP 123, syslog 514, SNMP 161, WinRM 5985 and 5986, and
   the common monitoring and backup agent ports). Where app labels exist,
   also run `identify-infrastructure-services` and merge its tiers. Write
   the hub list out; it is a deliverable in its own right and the user
   should confirm it before step 5.
5. Clustering. Edges between managed non-hub workloads, weight = log of
   connections plus a bonus per distinct port. Run seeded label propagation
   with existing app labels clamped and a hop attenuation of 0.5 as the
   first method; run Louvain with resolution 1.5 and split by components as
   the second. Where the two agree, confidence is high; where they
   disagree, show both memberships. Run the feature similarity pass (3.2)
   per cluster to propose roles.
6. Naming. For each cluster: majority existing app label among members (if
   purity at or above 0.8, propose that name); otherwise the dominant
   hostname token not shared with neighbouring clusters; otherwise the
   dominant process basename on the listening side (Guardicore's signal);
   otherwise a placeholder `candidate-app-NN`. Always attach the evidence:
   member count, members by hostname, top listeners with processes, inbound
   and outbound peer clusters, hubs it depends on, VIP-fronted flag, and a
   proposed membership rule (hostname regex or IP range) in Illumio
   labeling-rule form, following Cisco's "candidate queries" pattern.
7. Evaluation (section 5) on every run, printed at the top of the report,
   including cap-hit and hub-drop counts.
8. Review. The user names placeholders, merges and splits, and accepts or
   rejects membership rules. Accepted names become seeds for the next run
   (Cisco's approval loop). Nothing is written to the PCE by this skill;
   label writes stay in the advisor's existing flow.

Which signals first: hostname tokens before traffic (free, deterministic,
often decisive for env and loc); listening ports and processes before
traffic for role; traffic only for the app dimension and only after hub
removal. Existing labels first of all, as seeds and as ground truth.

Where it should live: a separate experimental skill (working name
`illumio-app-discovery`, marked experimental in its description) that
produces a cluster report and candidate labeling rules, which the label
advisor reads as one more input alongside hostnames and peer labels.
Reasons:

- The advisor's promise is per-workload suggestions from evidence the user
  can check row by row; clustering adds a global, non-deterministic step
  whose failures (a merged pair of apps) are invisible at row level. Keeping
  them apart keeps the advisor's output explainable.
- The data budget differs: the advisor can work from a handful of filtered
  traffic queries; discovery needs the whole managed graph, which on 3,000
  workloads is thousands of 500-row calls. That belongs behind an explicit
  opt-in, not a flag.
- The experiment needs its own evaluation harness and will be revised
  often; the advisor should only depend on its stable output format (cluster
  id, members, proposed name, confidence, rules).
- A flagged mode inside the advisor is the right end state only if the
  experiment shows pairwise precision above 0.8 on two or more real
  estates; until then the result is a report.
- Gap for the server (filed as illumio-mcp-server issue #82): a
  workload-level variant of `identify-infrastructure-services`, or a
  `group_by` that returns workload hrefs so the script does not have to
  resolve hostnames, would remove most of the query burden from step 3.

## 7. Risks and open questions

Risks:

- Query volume and truncation. Thousands of 500-row calls per run; hub
  destinations are exactly the rows that get truncated; recall numbers are
  only meaningful with the cap-hit count beside them.
- Smearing. One missed hub merges clusters; one over-aggressive threshold
  fragments them. The thresholds will be estate-specific and must be shown,
  not hidden.
- Load balancers and VIPs. Client-to-VIP flows end at an unmanaged IP;
  server tiers lose their consumers. Without virtual service objects from
  the PCE this will be a labelled limitation, not a solved problem.
- Label semantics. Illumio app labels are often coarser or finer than
  traffic communities (one label per product line, or one per environment
  instance). Ground truth may be wrong or inconsistent, and the metric will
  then punish a correct clustering. Spot-check disagreements by hand before
  trusting a number.
- Seed bias. Clamping existing labels propagates existing mistakes. Hold
  out a third and report whether held-out labels are recovered.
- Model cost. Reading cluster evidence for hundreds of clusters is a lot of
  JSON for the model; the script must produce a compact report and the skill
  must page through it.
- Container and ephemeral workloads. Kubernetes workloads and short-lived
  VENs churn membership; Cisco's granularity note about services versus
  pods applies. Exclude container workloads from the first experiment.
- Trust. A wrong app suggestion that becomes a ring fence breaks an
  application. Everything stays a suggestion with evidence and a rule the
  user can read; the skill never writes labels.

Open questions:

- Does the Explorer API honour `group_by` with workload identity so that a
  per-source query returns one row per (destination workload, port) rather
  than per IP? If yes, the row count per source drops well under 500 for
  most workloads.
- What is a sensible default window? Illumio recommends 14 days for core
  services detection; app structure probably needs 30 days or more to
  catch monthly jobs, which also raises the chance of batch edges.
- Can `identify-infrastructure-services` be extended server-side to run at
  workload level, with `min_connections` and fan thresholds exposed? That
  is the cleanest fix for unlabelled estates.
- Which estates are available for evaluation? The experiment needs at
  least one partially labelled estate with real traffic (demo100 or a
  customer lab), and ideally two with different naming conventions.
- Should custom label dimensions (customer-specific keys) be seeds, targets
  or ignored? They are often the dimension that most closely matches the
  traffic communities (business unit, service owner).
- How should the report present a cluster the user refuses to name? A
  rejected cluster should become a cannot-link constraint on the next run
  (Wagstaff et al. 2001 constrained clustering,
  https://cdn.aaai.org/AAAI/2000/AAAI00-180.pdf), which is a small addition
  to seeded label propagation.
